# 打分与分诊方法论

本文档说明 Echo 如何把"一堆文本"变成"本周该做什么"，以及每个数字怎么来。

## 从反馈到行动的链路

```
原始反馈 → 清洗(去重/过短/空行) → 语义向量(多语言MiniLM, 384维, L2归一化)
        → KMeans(k-means++初始化, 余弦距离, 3次重启取最优)
        → 自动定k(肘部法, 上限 ceil(n/8), 禁止碎片化)
        → 每簇统计 → 优先级分 → 四档动作
```

## 每簇统计量

| 统计量 | 定义 | 回答的问题 |
|--------|------|-----------|
| 影响面 share | 簇内反馈数 / 总反馈数 | 多少比例的用户在说这件事？ |
| 负面率 negativity | 簇内负面条数占比（评分≤2星；无评分时用情绪词表） | 说话的人有多不爽？ |
| 平均评分 avgRating | 簇内评分均值（如有） | 严重程度如何？ |
| 动量 momentum | 簇在近30天反馈中的占比 − 历史整体占比 | 这件事在恶化还是消退？ |

## 优先级分（0–100）

```
priority = clamp(
    35 × f(share)          # 影响面项，边际递减：+1% 声量在小簇里更值钱
  + 35 × negativity        # 负面率项，线性
  + 15 × clamp(4×momentum, -0.5, 1)   # 动量项：正在恶化的问题加分
  + 10 × rating_term,      # 低均分加分（无评分时取中性 0.3）
  0, 100)
```

设计意图：**影响面和负面率是大头（70分）**——归因台的第一要务是"最痛的事排最前"；动量占15分保证"正在恶化"会插队；评分只占10分，因为评分缺失/噪声在商店评论里很常见。

## 四档动作规则（lib/pipeline/score.ts · decideAction）

按顺序判定：

1. **🟢 好评**：纯好评（评分≥4星**且**非建议句式）占簇内 ≥50%
   - 为什么排除建议句式：4星"希望增加深色模式"按评分是正面，但它是路线图输入，放进"好评"桶会被拿去做传播素材，语义错位
2. **🔴 该修**：share ≥ 8% 且 negativity ≥ 50% —— 成规模的痛点
3. **🟡 该回**：negativity ≥ 30% 但声量未达该修线 —— 个体诉求，客服/运营逐条触达
4. **🔵 观察**：其余 —— 有声量但情绪混合，持续跟踪动量

## 主题命名

- **无 LLM**（默认）：簇内 TF-IDF top 关键词（中文按 2-gram + 词典切分）拼接为标题，如"闪退 · 崩溃 · 打开"
- **有 LLM**（BYOK）：把簇内代表性原声（3条medoid+随机样本）交给 LLM 起一个 ≤10 字的主题名 + 一句归纳

## 已知取舍

- **自动定 k 偏保守**：肘部法对"语义相近的负面主题"（登录/计费/客服）倾向合并。评测显示强制细分会碎片化且 ARI 下降，产品选择合并——运营视角"账号与服务问题"是一个可行动的工单。
- **情绪判定优先信评分**：有评分时评分≤2即负面，忽略文本情绪词；无评分（客服记录类）才走词表。这保证商店评论场景的高准确率。
- **动量需要日期**：无日期列时 momentum=0，优先级分仍可用但失去趋势维度；上传向导会提示补日期列。
